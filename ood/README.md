# Bhaskera in Open OnDemand

An interactive app: a user opens **Interactive Apps, Bhaskera**, picks an account, a partition and the hours, and gets Bhaskera's home page in a new tab,
signed in with the portal's own login. Under the hood the app starts a small CPU job as the user that runs `bhaskera-dashboard portal`; the portal's reverse
proxy (`/rnode/<host>/<port>/`) reaches it, and the page accepts only requests that carry the session token the portal's Connect button hands over.

## What is in here

| File | Purpose |
|---|---|
| `bhaskera/manifest.yml` | Name and place in the portal's menu |
| `bhaskera/form.yml.erb` | What the user chooses: Slurm account, partition, hours |
| `bhaskera/submit.yml.erb` | The session job: one node, 2 CPUs, 4 GB, the hours chosen |
| `bhaskera/template/script.sh.erb` | Loads the module, makes the user's own run folder from the shared kit on first use, starts the page |
| `bhaskera/view.html.erb` | The Connect button: posts the session password to the session address, which sets the cookie |

## Installing it (an administrator)

1. Copy `bhaskera/` to `/var/www/ood/apps/sys/bhaskera` (or, to try it first, to `~/ondemand/dev/bhaskera` of a user for whom the portal's *Develop* mode is enabled).
2. Set `OOD_BHASKERA_CLUSTER` (or edit `form.yml.erb`) to the cluster id: the name of the file in `/etc/ood/config/clusters.d/`.
3. Make sure the portal's `host_regex` lets `/rnode/` reach the compute nodes the session may land on.
4. Check the module name in `form.yml.erb` (`bhaskera/1.0.0`).

## What was tested, and what was not

Tested on PARAM Rudra, without the portal itself:

- `bhaskera-dashboard portal` as a job on a compute node, reached from a login node over the network: no token or a wrong token gives 403; the right token gives a cookie;
  with the cookie the page, the user's runs, models and own tests load; *Check first* for a training recipe runs inside the job.
- In a real browser, behind a proxy that strips a `/rnode/<host>/<port>` prefix: the form post sets the cookie, every request is relative to the page, the Start dialog loads.

Not tested (needs the portal and an administrator):

- The app inside Open OnDemand itself: that the portal's proxy reaches the session, passes `Set-Cookie`, and accepts the form post.
- Starting a training job from the page inside the session (it uses the user's own `sbatch`), and the chat window, which reaches a chat server on another node over SSH:
  that needs SSH between compute nodes where the user has a job.
- Many users at once, and a user opening a second session.

## What the page does not show behind the portal

The links to MLflow's own pages and to each job's Ray Dashboard use `*.localhost` host names that only work through the SSH tunnel of the stand-alone page, so they are
hidden here. Runs, Models, Compare, the logs, Start, Chat and Benchmark read the same files directly and work.

## How the access is protected

- The session job runs as the user, with the user's own Slurm account, files and limits; nothing is shared between users.
- The page listens on the node's network address, so any cluster user's process could try to connect: it answers only a request that carries a 24-character random token
  (generated by the portal for each session). A cookie (`HttpOnly`, `SameSite=Lax`) carries it after the first visit; changes also need a header only the page's own script sends.
- The token lives in the session job's environment and in the portal's session record, as for the portal's other interactive apps.
